# 微信公众号自动化内容流水线 · 可行性评估

> 评估对象：复用「每日新闻」项目的采集思路，围绕「AI 薅羊毛信息」「AI 打假」两类选题，自动抓取素材 + 配图 + 排版 + 推送到公众号草稿箱
> 评估时间：2026 年 10 月
> 评估依据：本机 `每日新闻/` 现有代码与产物、`.workbuddy/automations/` 运行记录、微信公众平台现行接口规则

## 一、结论先行

**总体：技术上可行，而且比你想的更容易——因为你已经有 60% 了。但商业上有个硬伤，不在技术层。**

三条判断：

1. **链路后半段几乎不用自己造。** 草稿箱 API 对个人未认证订阅号是**实测可用**的（这一点网上大量教程说错了，说"个人号只能手动复制粘贴"是错的）。你要新建的其实是配图、排版转换、推送这三个模块，都是纯工程问题，几天能跑通。
2. **"完整链路"的终点只能是草稿箱。** 发布接口（`freepublish/submit`）2025 年 7 月起已对个人主体回收，返回 48001。而且微信**没有开放的定时发布 API**——网页后台的"定时发表"没有开给接口。所以"自动发布"这个词要从你的方案里删掉，正确说法是"自动建稿 + 人工点发布"。
3. **最大的风险不在技术，在选题本身。** 「AI 打假」是公众号里法律风险最高的内容类型之一——你指控别人造假，举证责任在你；「AI 薅羊毛」则天然挨着虚假宣传、诱导分享和灰产。这两块如果照现在的字面意思做，翻车概率远高于技术故障。

**分环节红黄绿灯：**

| 环节 | 可行性 | 判断 |
|---|---|---|
| 素材采集 | 🟢 高 | 现有方法论可直接复用，但需补去重 |
| 配图 | 🟡 中 | 技术上简单，版权上高危，建议自建视觉模板 |
| 排版 | 🟢 高 | 纯工程，有明确踩坑清单，1-2 天可稳定 |
| 草稿箱推送 | 🟢 高 | 实测可用，坑集中在参数限制和编码 |
| 自动发布 | 🔴 不可行 | 接口已回收 + 平台明令禁止，不要尝试 |
| 选题本身 | 🔴 高危 | 需要重新设计表述和边界 |

## 二、先厘清一件事：你现在没有"抓取器"

这是评估里最需要纠正的认知偏差。

你说"复用原项目中获取科技新闻的思路，自动抓取新闻"。但看了代码，**`每日新闻/` 里没有任何爬虫**。三个脚本分别是：

| 文件 | 实际职责 |
|---|---|
| `脚本/common.py` | 解析已生成的 md（正则匹配标题/简述/来源），**不联网** |
| `脚本/score.py` | 对 md 做确定性打分（情绪/热度/副业四维），**不联网** |
| `脚本/export_web_data.py` | md → JSON 导出给前端，**不联网** |

真正的"采集"发生在自动化 prompt 里：**由我（LLM）调用 WebSearch 多源检索，然后直接写成 md**。所以你现在跑通的是「智能体检索 + 生成」，不是「爬虫抓取」。

这个区别决定了后面所有的稳定性判断：

| | 智能体检索（现状） | 爬虫抓取（你想的） |
|---|---|---|
| 可复现性 | 低，每天结果不同 | 高，可 diff |
| 覆盖保证 | 无，靠搜索排序 | 可枚举，不漏 |
| 时效 | 快（分钟级） | 取决于抓取频率 |
| 维护成本 | 几乎为零 | 高（反爬、页面改版） |
| 法律风险 | 低（读公开网页） | 中（robots、数据库权利） |
| 事实可靠性 | **中低**（搜到的常是二手 AI 农场站） | 中（取决于源） |

**建议：不要推翻现状去写爬虫，而是补一个"线索池"。** 用 RSS/官方 API（arXiv、Hacker News、GitHub Trending、少数科技媒体 RSS）做"不漏"的底座，智能体检索做"深挖与验证"。这样既保留现有能力，又补上了可复现和去重。

**关于打假资产，值得单独说：** 我看了 2026-10-23 那篇打假产物，质量是超出预期的——引了 arXiv 编号（2610.22319）、作者名、4 个独立源，而且**主动指出了论文自身的局限**（单次运行、Easy 难度、22% 程序报错），最后给出"核心事实靠谱但叙事夸大"的分级结论。这个范式（原始信源 + 局限说明 + 分级评级）就是对抗名誉权风险的正确答案，可以直接固化成 SOP。

## 四、逐环节技术可行性

### 4.1 素材采集（🟢 高，但要去重）

**三方案对比：**

| 方案 | 稳定性 | 覆盖 | 开发量 | 建议 |
|---|---|---|---|---|
| A. 智能体检索（现状） | 中 | 靠搜索 | 0 | 保留，用于深挖和验证 |
| B. RSS / 官方 API | 高 | 可枚举 | 小（半天） | **新增，做线索池** |
| C. 网页爬取正文 | 低 | 高 | 大 | 不建议做主语料 |

**为什么推荐 A+B 混合：** B 负责"今天有哪些事"（不漏、可去重、可 diff），A 负责"这件事到底怎么回事"（读多篇报道、找原始信源）。这也正好匹配你现有的打假环节——打假需要的是"深挖"，不是"广扫"。

**必须补的两个机制：**

1. **去重与事件指纹。** 每天同一件事会被 20 个站转载，不做去重会产出"看起来 5 条其实 1 条"的内容。做法：
   - URL 规范化（去 utm 参数、统一协议、去尾部斜杠）
   - 标题相似度（编辑距离 / 分词后 Jaccard）
   - **事件指纹 = 主体实体 + 动作 + 关键数字**（如"Gemini/通关/605 次死亡"），比标题更稳
2. **信源分级。** AI 新闻领域现在有一个很麻烦的现象：大量 SEO 农场站互相抄，而且它们的内容本身已经是 AI 生成的。如果你抓的是"转载的转载的 AI 摘要"，做二次加工后再发，事实链条已经非常脆。
   - 一级源：论文（arXiv DOI）、官方博客/公告、财报、GitHub Release → 可直接引用
   - 二级源：有署名记者的科技媒体 → 需两源独立印证
   - 三级源：聚合站、内容农场、无署名快讯 → **只作线索，不作证据**

### 4.2 配图（🟡 中，全链路最弱一环）

这是你现在完全没有的部分，也是我认为**不该按"抓取新闻配图"来做**的部分。三个硬约束：

**约束一：外部图片在公众号正文里不显示。**
微信正文只认自己的 CDN（`mmbiz.qpic.cn`）。你 HTML 里写 `<img src="https://other-site.com/a.jpg">`，在编辑器里可能预览正常，发出去就裂图或被过滤。正确做法是调 `media/uploadimg`（上传图文消息内图片），拿回微信 URL 再替换 `src`。这一步不做，整篇配图全废。

**约束二：防盗链。**
新闻站的图普遍有 Referer 校验，直接下载返回 403。技术上可以伪装 UA/Referer 绕过——但"伪装请求头批量抓取他人图片"，性质上已经不是"阅读公开网页"了。

**约束三：版权是最容易赔钱的地方。**
新闻配图 99% 有版权，"合理使用"的边界在中国司法实践里很窄，公众号未经授权使用他人新闻图片是著作权索赔的高发点，单张判赔常见几百到几千元。而且这一类风险有个讨厌的特征：**你越火越容易被告**（维权方按阅读量挑目标）。

**结论：不要抓图。自建三套零版权视觉资产，反而更好。**

| 方案 | 版权 | 风格统一 | 实现 |
|---|---|---|---|
| **① 卡片模板出图（推荐）** | 零风险 | 最好 | 用 SVG/HTML 模板 + 无头浏览器截图，或 Python Pillow 直接画 |
| ② AI 生图 | 有（需遵守标识办法，且打假文配 AI 图自相矛盾） | 中 | 一句提示词 |
| ③ 免费商用图库（Unsplash/Pexels） | 低风险 | 差，新闻感弱 | 需人工选 |

**为什么 ① 最适合你这两个选题：**
- 「打假」最合适的视觉就是**"传言 vs 事实"对比卡**——左边红底放传言原文，右边绿底放核查结论 + 评级星级。这种卡片只能自己做，AI 生图做不出版式。
- 「薅羊毛」最合适的是**"信息卡"**：工具名 + 免费额度 + 有效期 + 入口。同样只能自己做。
- 好处：版式固定 → 批量生成 → 视觉识别度高 → 长期看是账号资产。

具体实现：一个 `render_cover.py`，输入 JSON（标题、副标题、评级、标签），输出 900×500 的 PNG。Pillow 画矩形和文字即可，不依赖浏览器，跑得快、无外部依赖。

### 4.3 排版（🟢 高，坑很明确）

**核心原理一句话：公众号编辑器会剥离所有 `<style>` 标签和 class，只保留内联 `style="..."`。** 现有 `web/` 那套是给浏览器看的，完全不能复用。

**已确认的踩坑清单（多条独立实测来源一致）：**

| 坑 | 现象 | 解决 |
|---|---|---|
| `<style>` / class | 全部样式丢失，白底黑字 | 每个标签写内联 style |
| `<ul>/<li>` | bullet 错位、被当成二级列表 | 改用 `p` + 背景色/左边框的 `blockquote` 平铺 |
| `<table>` | 渲染不稳、列宽错乱 | 表格改成"每行一个 blockquote 块" |
| 混入 Markdown 语法 | 编辑器空白 + 提示"正文违规" | 必须先完整转成纯 HTML 再提交 |
| 深色模式 | 硬编码浅色背景时文字看不清 | 背景色不要太白，字色不要纯黑 |
| `<pre>` 代码块 | 不一定保留 | 转成表格或带底色的 p |

**技术选型建议：** 不要自己写 Markdown 解析器。用 Python `markdown` 库转 HTML，然后过一遍"内联样式注入器"（用正则或 BeautifulSoup 给每个标签加 style）。这条链最短、最稳。现成工具（md2wechat、doocs/md）也可以，但自己控样式更好调。

**验收标准：** 同一篇稿子在 iOS 微信、Android 微信、PC 微信、深色模式四端各看一遍，无错位、无裂图、无看不清。

### 4.4 草稿箱推送（🟢 高，有明确参数陷阱）

**这条链路是成立的，而且个人号能用。** 完整链路：

```
GET /cgi-bin/token                     → access_token（7200s）
POST /cgi-bin/media/uploadimg           → 正文图 URL（每张图）
POST /cgi-bin/material/add_material     → 封面 media_id（type=image）
POST /cgi-bin/draft/add                 → 草稿 media_id
（人工）浏览器后台点「发表」              → 发布
```

**关键事实澄清（这点很多人被旧教程误导）：**

| 接口 | 个人未认证订阅号 | 说明 |
|---|---|---|
| `draft/add` 建草稿 | ✅ **实测可用** | 网上说"个人号 48001 用不了"是错的 |
| `material/add_material` 传封面 | ✅ 可用 | |
| `media/uploadimg` 传正文图 | ✅ 可用 | |
| `draft/batchget` 读草稿 | ✅ 可用 | 可用于幂等查重 |
| `freepublish/submit` 发布 | ❌ 48001 | 2025.7 起回收 |
| `message/mass/send` 群发 | ❌ 48001 | 同上 |
| 定时发布 | ❌ 无 API | 网页后台有，但没开放给接口 |

**已确认的实测参数限制（文档没写清，只能试出来）：**

| 字段 | 文档说法 | 实测限制 | 报错码 |
|---|---|---|---|
| `title` | 32 字 | 有反馈约 11 字即报错 | 45003 |
| `digest` | 128 字 | 约 54 字符 | 45004 |
| `author` | — | 约 2 个汉字（6 字节） | 45110 |
| `thumb_media_id` | 可空？ | **必填**，缺了报错 | 40007 |

> 建议：推送前先做本地长度校验（title ≤ 20 字、digest ≤ 50 字符、author ≤ 6 字节），不要等接口报错再改。

**四个必踩的坑：**

1. **中文变 `\u4f60\u597d`。** Python `requests.post(json=...)` 内部 `ensure_ascii=True`。必须手动 `json.dumps(data, ensure_ascii=False).encode("utf-8")` + `Content-Type: application/json; charset=utf-8`。
2. **IP 白名单。** 你在本机跑（动态 IP + 可能走代理），出口 IP 和 `ifconfig.me` 看到的可能不是同一个。做法：按报错信息里微信返回的那个 IP 去加，别猜。
3. **access_token 全局唯一。** 同账号在 A 处刷新会顶掉 B 处的旧 token。多个任务必须共用一个带缓存的 token 管理器，不能各写各的。
4. **幂等。** `draft/add` 每调一次就新建一条草稿，重跑一次草稿箱就多一条。必须：调用前 `draft/batchget` 查当天是否已有同标题草稿 → 有则 `draft/delete` 或跳过；本地写 `draft_status.txt` 记录 `media_id`。**这套机制你的 `send_status.txt` 已经跑通了，直接照搬。**

**另一个容易忽略的返回字段：** `draft/add` 返回里的 `ad_count` 非 0，表示微信检测到广告位或敏感词提醒——不是错误，但说明这篇有需要人工确认的地方，应该记进状态文件提醒你。

## 五、风险矩阵（按严重度排序，不按概率）

技术风险都可以修，下面这五条修不了，只能靠流程设计规避。

| # | 风险 | 概率 | 后果 | 控制措施 |
|---|---|---|---|---|
| 1 | **打假打错，构成名誉侵权** | 中 | 高（民事赔偿 + 删文道歉，个人主体自己赔） | 见 5.1，这是本次评估最重要的一节 |

### 5.1 「AI 打假」为什么是最高危的选题

《民法典》第 1025 条：为公共利益实施新闻报道、舆论监督等行为，影响他人名誉的，不承担民事责任——**但**有三个例外：① 捏造、歪曲事实；② 对他人提供的严重失实内容**未尽到合理核实义务**；③ 使用侮辱性言辞。

翻译成人话：**打假这个动作本身受保护，但你的"核实义务"标准比普通报道更高。** 而 AI 时代有个特别阴险的陷阱——你以为的"多源印证"，很可能 4 个源都是互相抄的同一篇。这种情况在法律上不叫"已核实"，叫"未尽合理核实义务"。

**必须固化的四条规则：**

1. **只引一级源。** 论文要有 DOI/arXiv 编号且可打开，公告要是官方域名，数据要是财报原文。"多家媒体报道"不算证据链。
2. **机器校验引用。** 所有 URL 做 HTTP 可达性检查 + 标题比对，失败即阻断发布。防 AI 编造引文。
3. **必须写明对方的局限或回应。** 你现有 10-23 那篇做对了——引了论文自身承认的四条局限。有这一段的打假文，风险等级直接降一档。
4. **词要降级。** 这条最便宜也最有效：

| 别用 | 改用 | 为什么 |
|---|---|---|
| 打假 / 造假 / 骗局 | **存疑 / 核验 / 值得注意** | "造假"是定性指控，"存疑"是陈述核查状态 |
| 辟谣 | **事实核验** | "辟谣"隐含"我有权定性" |
| 某某在骗人 | **该说法与原始信源不符** | 把"指控人"变成"陈述差异" |
| 割韭菜 / 智商税 | **信息不对称 / 溢价过高** | 侮辱性言辞是 1025 条的例外之一 |

栏目名建议从「谣言粉碎机」改成「**AI 说法核验**」或「**本周存疑清单**」。同样内容，法律风险完全不是一个量级。

### 5.2 「AI 薅羊毛」的边界在哪

"薅羊毛"这个词本身没问题，问题在它下面混着三类完全不同的东西：

| 类型 | 举例 | 判断 |
|---|---|---|
| 🟢 可做 | 大模型免费额度、限时免费工具、开源平替、官方学生优惠 | 信息真实、无返利、无门槛 |
| 🟡 谨慎 | 需要邀请码/返利链接的 | 属广告，需标识；部分平台返利链接本身违规 |
| 🔴 不能碰 | 批量注册、多账号套现、刷单、盗用优惠券、信用卡套现、代下代付 | 涉诈骗/破坏计算机信息系统/金融违规 |

另外三个具体雷：
- **不得承诺"必得"**。"人均可领 500 元"这类表述属虚假宣传，实际领不到就是问题。
- **不得诱导分享**。"转发到 3 个群解锁"是明确的平台违规项。
- **必须标有效期**。薅羊毛信息半衰期常常只有几小时到几天，而你这条链路是"晚上采集、早上发布"，等的这段时间里信息可能已经过期。**建议：每条信息强制带 `deadline` 字段，超过 72 小时的不发；发了的，过期后在文末补一句"该活动已于 X 日结束"。**

**选题改造建议（这是我最想让你改的一点）：**

把「AI 薅羊毛」改成「**AI 工具免费额度月度盘点**」或「**本月值得关注的 AI 免费/开源方案**」。原因：
- 信息生命周期从"几小时"变成"一个月"，跟你月更的副业榜节奏天然匹配（你已经有 `创意/副业榜/2026-10.md` 这个资产）
- 天然没有返利链接、没有灰产空间
- 和"副业机会"选题形成系列，账号标签更聚焦，比"薅羊毛"这种泛词更容易被算法打准

## 六、分阶段落地计划

按"先验证不可行性，再投入建设"的顺序排——这是省钱的做法。

| 阶段 | 内容 | 工时 | 验收标准 |
|---|---|---|---|
| **P0** | 只做一件事：拿 AppID/AppSecret + 加 IP 白名单，用 curl 调一次 `draft/add` 推一篇测试稿 | 1 小时 | 草稿箱里出现一篇（含中文、含封面）。**这一步不通，整个方案重做** |
| **P1** | 排版引擎：md → 内联样式 HTML，四端验证 | 1-2 天 | 手机上无错位、无裂图 |
| **P2** | 推送脚本：长度校验 + token 缓存 + 编码 + 幂等（含 `draft_status.txt`） | 1 天 | 同一天重跑 3 次，草稿箱仍只有 1 篇 |
| **P3** | 封面卡片生成器（固定场景 + IP + 文字层，Pillow/SVG 模板出图，零版权） | 1 天 | 900×383 首图 + 1:1 分享图，样式统一，3 秒出图；换文字不换底版 |
| **P4** | 线索池 + 去重（RSS/API + 事件指纹） | 2-3 天 | 同一天不出现重复事件 |
| **P5** | 引用校验闸门（URL 可达 + 标题比对）+ 人工审核状态机（`pending_review` → `approved`） | 1-2 天 | 故意塞一个假 URL，必须被拦下 |

**总计约 8-10 个工作日**，其中 P0 决定成败、P5 决定安全。

**不建议做的（明确划掉）：**

- ❌ 自动发布（接口没了 + 平台明令禁止）
- ❌ 网页爬取正文做主语料（不稳定 + 法律风险，收益不匹配）
- ❌ 抓取他人新闻配图（最高频索赔点）
- ❌ 浏览器自动化去"点发表"（技术上能做，但性质上就是"自动化替代真人完成发布流程"，正好撞在 2026.3 那条规则上）

最后一条值得多说一句：有人会用 Selenium/Playwright 模拟点击绕过接口限制。**技术上可行 ≠ 合规。** 平台判定违规看的是行为特征（同一时间固定推送、内容批量生成、无人工编辑痕迹），不是看你走了哪个接口。

## 七、和「非真人自动化创作」红线的距离

这是整个方案最需要自省的地方。2026 年 3 月 27 日新增的规则，禁止的是"利用 AI、脚本、接口或其他自动化方式，**替代真人**完成内容创作、发布等流程"。关键词是"替代"。

对照你的方案：

| 环节 | 现状设计 | 判定 |
|---|---|---|
| 采集 | 机器检索 | ✅ 允许（工具） |
| 事实核验 | 机器交叉 + 人复核 | ✅ 允许，且是加分项 |
| 写作 | 机器生成初稿 | ⚠️ 取决于人工改写深度 |
| 排版 | 机器转换 | ✅ 允许（工具） |
| 推草稿箱 | 机器 | ✅ 允许 |
| 发布 | 人工点 | ✅ 合规 |

**所以你的方案在结构上是合规的**——因为终点设在草稿箱，人工必须出现。但这只是"结构合规"，还有"实质合规"：

> 如果人工那一环退化成"看一眼就点发布"，实质就是自动化创作，只是多了一次点击。这种号的特征很显眼：同一个时间点、同样的结构、没有个人经历、没有对读者的回应——平台是能识别出来的。

**建议在流程里加两条硬约束：**

1. **每篇必须有人的痕迹**：至少一段是你自己写的（个人判断/经验/吐槽），且这段不能被模板化。
2. **保留版本记录**：`初稿.md` → `人工修改.md` 两个版本都留。万一被判定，这是你申诉"真人创作"的唯一证据。你的归档目录结构加一层 `drafts/` 就行。

## 八、对标账号拆解：硅基章鱼

这个号是「AI 福利/信息差」赛道里模板化做得最彻底的一类，值得逐层拆。它的价值不在于流量（下面会说明），而在于**它把封面做成了可批量生产的资产**——这正好是你 P3 环节要的答案。

### 8.1 它到底在做什么

**定位一句话：** 简介写的是「获取资源永远比别人更快一步，让你的 AI 世界没有信息差」。这不是内容号，是**信息中介号**——卖的是"快"，不是"深"。

**内容结构（从标题反推）：**

| 发布 | 封面大标题 | 副标题 | 结构 |
|---|---|---|---|
| 昨天 | 两份 AI 福利 | OpenCode 免费模型 / WorkBuddy 教师专属 · 每月 2000 积分 | 数量 + 产品 + 额度 |
| 星期三 | 配音演员也要失业了？ | AI 配音免费用 / Fish Audio | 焦虑钩子 + 免费 |
| 星期二 | AI 做个小网站 | 领 18 元奶茶券 / Qoder 新用户福利 | 场景 + 具体金额 |
| 星期二 | GLM-5.3 | 免费试 5 天 / ZCode 新用户福利 | 型号 + 时效 |

**规律非常清晰：**

1. **标题里必须有可量化的具体数字。** "两份""2000 积分""18 元""5 天"——薅羊毛类内容的核心是"数字即诱惑"，"免费"两个字单独出现没有力量，"免费 5 天""每月 2000 积分"才有。
2. **三段式：利益点 → 具体产品 → 时效/额度。** 读者扫一眼就知道值不值、是什么、还剩多久。这三条缺一条，点击率就掉。
3. **偶尔用行业焦虑做钩子**（配音演员失业），但立刻落到"免费"。这是唯一带情绪的一类，其余全是冷静的信息陈述——因为受众要的是效率，不是共鸣。
4. **发布时间密集**（星期二出现两条）。见 8.3，这是个重要的运营杠杆。

### 8.2 封面模板：这是最值得抄的部分

拆开看，它的封面只有四个图层，而且**三个是固定不变的**：

| 图层 | 内容 | 是否变化 | 每期改动成本 |
|---|---|---|---|
| ① 场景底图 | 浅色木质桌面 + 笔记本电脑 + 绿植 + 白墙 | **固定** | 0 |
| ② IP 形象 | 蓝色小章鱼（不同姿态：戴耳机、看书、坐桌前） | 半固定（3-5 个姿态轮换） | 0 |
| ③ 文字层 | 三段式大标题 | **可变** | 改 3 行字 |
| ④ 产品层 | 产品 logo / 界面截图 / 官方活动图 | **可变** | 换 1 张图 |

所以它的单张封面生产成本 ≈ **改三行字 + 换一张截图**。这就是为什么它能一天发多篇还不崩——**瓶颈不在设计，在信息获取**。

**为什么这套视觉有效（三个机制）：**

- **高辨识度**：深蓝字 + 浅暖底，在订阅号信息流的白色卡片里对比很强，缩略图阶段就能看清。
- **IP 做视觉锚点**：章鱼反复出现，读者不必读标题就能认出是这个号。长期看，这比任何 logo 都值钱。
- **场景化降低"广告感"**：桌面/笔记本电脑/绿植是"在用工具"的场景，不是"在打广告"的棚拍。这层心理暗示对福利类内容很关键——读者要觉得自己是在看"别人正在用的东西"，不是看促销。

**对你的直接启示：** 我上一轮建议的"自建卡片模板"完全成立，而且可以做得比它更省——它还需要 AI 生成场景图（有成本、有 AI 标识义务），你直接用 SVG/Pillow 画扁平色块场景即可，零成本、零版权、可无限批量。P3 就按这个四图层结构做：底图固定、IP 固定、文字层参数化（标题/副标题/额度）、产品层留一个图片槽。

### 8.3 一个被忽略的运营杠杆：发表 ≠ 群发

截图里星期二出现两条，说明它一天发了不止一次。这里有个很多人不知道的机制：

| | 群发 | 发表（不勾"群发通知"） |
|---|---|---|
| 是否推送给粉丝 | 是，有红点提醒 | **否，静默** |
| 次数限制 | 订阅号 1 次/天 | **不限次数** |
| 是否占群发额度 | 占用 | **不占用** |
| 能否进推荐流/搜一搜 | 能 | **能** |
| 出现在账号主页 | 是 | 是 |

**这对你的方案是决定性的。** 薅羊毛类信息的半衰期常常只有几小时到几天，用群发（1 次/天）根本跟不上——早上 8 点群发一次，下午 3 点出现的福利就废了。正确策略：

- **重要内容（月度盘点、核验长文）→ 群发**，占当天唯一额度，推到粉丝面前。
- **福利快讯 → 发表**，一天 2-3 条，不打扰粉丝、不占额度、照样吃搜一搜和推荐长尾。

这样你的自动化一天可以产出多条草稿，你只需要挨个点"发表"时决定勾不勾那个开关。**注意：草稿箱 API 不控制这个开关**（`need_open_comment` 是留言开关，不是群发开关），所以这一步必须在后台手动选——正好，它天然成了人工把关点。

### 8.4 但要看清它的天花板

数据说话：`阅读 89 / 121 / 29`，`赞 4 / 3 / 2`，57 篇原创。

**这个号还很小，而且这套打法不产生爆款。** 它的模式是"高频 + 精准刚需 + 长尾搜索"，靠累计而不是靠单篇引爆。所以：

- ❌ 不要指望抄了这个模板就有流量。模板解决的是"生产成本"，不解决"分发"。
- ❌ 不要以为"信息差"是好生意。信息差的窗口正在关闭——2026 年做 AI 福利号的密度极高，同一份福利 20 个号在发，读者没有理由只看你。
- ✅ 但它验证了一件事：**这类内容的产能瓶颈在"信息获取速度"，不在"写作"。** 而这恰恰是自动化最有价值的地方——你现有的多源检索能力，就是它的人工成本的替代品。

### 8.5 你要比它多做的两件事（否则你就是第 21 个搬运号）

**第一，加"实测"。** 「教师专属 2000 积分」这种信息，只有真的去领过、知道卡在哪一步、知道要不要审核、知道名额什么时候没，才写得出来。纯搬运的号只能写"官方说可以领"，你能写"我领到了，但要先做 X，否则卡在 Y"。**这一句话就是你和它的全部区别。**

**第二，加"核验"。** 你已经有打假/核验的能力和 SOP（多源交叉 + 分级评级），这是绝大多数福利号没有的。福利信息里混着大量过期、缩水、假活动（"点击领取"实为拉新），做一期「本月 5 个 AI 福利实测：3 个能领，2 个是坑」，这种内容它做不出来，而且天然规避了"纯搬运"的低创作度判定。

**这也是解决 5.2 那节合规问题的正解：** 不是不写福利，是写成"我试过了"的形式。前者是搬运（低创作度 + 虚假宣传风险），后者是体验（原创 + 有个人痕迹）。

## 九、如果只做三件事

1. **今天就花 1 小时验证 P0。** 拿到 AppID/AppSecret，加 IP 白名单，curl 推一篇测试稿。这一步的结果决定后面所有投入是否成立——不要先写排版器再发现接口不通。
2. **把栏目名从「打假」改成「核验」。** 零成本，法律风险降一档，而且更符合平台对"舆论监督"的认定。
3. **配图改成自建卡片模板。** 不抓图、不生图，用 Pillow 画"传言 vs 事实"对比卡和"信息卡"。省掉版权风险，还顺便获得了视觉识别度。
